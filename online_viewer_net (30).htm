بوابة الإنترنت

Internet Gateway
سهل

شركة ناشئة تبني موقع تجارة إلكترونية على AWS. أنشأت VPC بـ CIDR 10.0.0.0/16 وشبكة فرعية 10.0.1.0/24 وأطلقت خادم الويب EC2 فيها. عندما يحاول العملاء الوصول إلى الموقع، لا يصلهم أي رد.

A startup built a public e-commerce site on AWS. They created a VPC (10.0.0.0/16) and a subnet (10.0.1.0/24) with an EC2 web server. Customers can't reach the site.

ما الأرجح أنه ناقص، وما الخطوتان اللازمتان للإصلاح؟

What is most likely missing, and what are the two steps needed to fix it?

✔ الإجابة

الناقص هو Internet Gateway. الخطوات:
(١) أنشئ Internet Gateway وقم بإرفاقه بالـ VPC.
(٢) أضف مساراً في جدول توجيه الشبكة الفرعية: الوجهة 0.0.0.0/0، الهدف = الـ IGW.
هذا يجعل الشبكة الفرعية عامة ويتيح حركة مرور الإنترنت الواردة والصادرة.

An Internet Gateway is missing. Steps: (1) Create and attach an Internet Gateway to the VPC. (2) Add a route in the subnet's route table: destination 0.0.0.0/0, target = IGW. This makes the subnet public and allows internet traffic.

بوابة NAT

NAT Gateway
متوسط

شركة تُشغّل تطبيقاً مصرفياً على AWS. خوادم قواعد البيانات موضوعة في شبكة فرعية خاصة لأسباب أمنية. يحتاج الفريق إلى تنزيل التحديثات والتصحيحات الأمنية من الإنترنت، لكن يجب ألا يتمكن أحد من الوصول إلى الخوادم من الخارج.

A banking app runs on AWS with DB servers in a private subnet. The team needs those servers to download updates from the internet — but the servers must NOT be reachable from outside.

ما المكوِّن الذي يجب على الفريق تهيئته، وأين يجب وضعه؟

What AWS component should the team configure, and where should it be placed?

✔ الإجابة

يجب استخدام NAT Gateway ووضعه في الشبكة الفرعية العامة (Public Subnet)، ثم تحديث جدول توجيه الشبكة الخاصة لتوجيه حركة الإنترنت (0.0.0.0/0) إلى الـ NAT Gateway. هذا يتيح الحركة الصادرة فقط، دون السماح بأي اتصال وارد من الإنترنت.

Use a NAT Gateway placed in the public subnet. Update the private subnet's route table to send 0.0.0.0/0 traffic to the NAT Gateway. This allows outbound-only internet access — no inbound connections from the internet are permitted.

CIDR والعناوين المحجوزة

CIDR & Reserved IPs
صعب

مهندسة حلول تصمم VPC لنظام جامعي. أنشأت VPC بـ CIDR 172.16.0.0/16 وتريد تقسيمها إلى ٤ شبكات فرعية متساوية. تحتاج كل شبكة فرعية إلى دعم ما لا يقل عن ٢٥٠ عنوان IP قابلاً للاستخدام لأجهزة الطلاب.

A solutions architect designs a VPC (172.16.0.0/16) split into 4 equal subnets, each needing at least 250 usable IP addresses for student devices.

ما الحجم الأدنى للشبكة الفرعية (CIDR prefix)، وكم عنوان IP قابل للاستخدام ستحتوي كل شبكة؟

What is the minimum subnet size (CIDR prefix), and how many usable IPs will each subnet have?

✔ الإجابة

يجب استخدام شبكات فرعية بـ /24 (مثال: 172.16.0.0/24). الـ /24 يعطي ٢٥٦ عنوان IP إجمالاً. تحجز AWS ٥ عناوين لكل شبكة فرعية، مما يترك ٢٥١ عنواناً قابلاً للاستخدام — وهذا يستوفي متطلب الـ ٢٥٠. الـ /25 يعطي فقط ١٢٣ قابلاً للاستخدام وهو غير كافٍ.

Use /24 subnets (e.g. 172.16.0.0/24). A /24 gives 256 total IPs. AWS reserves 5 per subnet → 251 usable IPs, meeting the 250 requirement. A /25 gives only 123 usable IPs — insufficient.

جداول التوجيه

Route Tables Misconfiguration
متوسط

مطورة في شركة اتصالات لديها شبكتان فرعيتان: شبكة عامة (10.0.1.0/24) بها خادم ويب، وشبكة خاصة (10.0.2.0/24) بها قاعدة بيانات. لاحظت أن قاعدة البيانات يمكن الوصول إليها من الإنترنت — وهذا انتهاك أمني خطير.

A developer has a public subnet (web server) and a private subnet (database). She notices the database is reachable from the internet — a serious security violation.

ما الخطأ في الإعداد الذي يتسبب في هذه المشكلة؟

What is most likely the misconfiguration causing this issue?

✔ الإجابة

على الأرجح أن جدول توجيه الشبكة الخاصة يحتوي على مسار يوجّه 0.0.0.0/0 إلى الـ Internet Gateway، مما يجعلها تتصرف كشبكة عامة. الحل: احذف ذلك المسار من جدول توجيه الشبكة الخاصة. يجب أن تحتوي الشبكات الخاصة فقط على المسار المحلي (10.0.0.0/16 → local).

The private subnet's route table likely has a route 0.0.0.0/0 → IGW, making it behave like a public subnet. Fix: remove that route. Private subnets should only have the local route (10.0.0.0/16 → local).

عنوان IP مرن وواجهة الشبكة

Elastic IP & ENI
صعب

شركة تقنية مالية تُشغّل خادم معالجة مدفوعات حيوياً على EC2. للخادم عنوان IP عام محدد مُدرج في القائمة البيضاء لدى عدة بنوك شريكة. تعطّل الـ EC2 instance ويجب إطلاق instance جديد فوراً. الفريق قلق من فقدان عنوان الـ IP المُدرج.

A fintech server has a whitelisted public IP used by partner banks. The EC2 instance crashes and a new one must be launched. The team fears losing the whitelisted IP.

ما ميزة AWS التي كان ينبغي استخدامها لمنع هذه المشكلة، وكيف تعمل؟

What AWS feature should they have used to prevent this, and how does it work?

✔ الإجابة

يجب استخدام Elastic IP Address. إنه عنوان IPv4 عام ثابت مرتبط بحساب AWS وليس بالـ instance. عند تعطّل instance، يُعاد ربط نفس الـ Elastic IP بالـ instance الجديد — ولن تلاحظ البنوك الشريكة أي تغيير. ملاحظة: الـ Elastic IPs غير المستخدمة تُكبّد رسوماً، لذا يجب تحريرها عند انتهاء الحاجة.

Use an Elastic IP Address — a static public IPv4 tied to the AWS account, not the instance. When the instance fails, re-associate the same Elastic IP to the new instance. Partner banks see no IP change. Note: unused Elastic IPs incur charges — release them when done.

الـ VPC والمناطق

VPC Scope & Availability Zones
سهل

طالب يتعلم AWS سأل: "هل يمكنني إنشاء VPC واحدة تمتد عبر منطقتين مختلفتين (Regions)؟ وهل يمكن للشبكات الفرعية أن تمتد عبر مناطق توافر (Availability Zones) متعددة؟"

A student asks: "Can I create a single VPC that spans two different AWS Regions? Can subnets span multiple Availability Zones?"

ما الإجابة الصحيحة لكلا السؤالين؟

What is the correct answer to both questions?

✔ الإجابة

لا في كلتا الحالتين. الـ VPC مرتبطة بمنطقة (Region) واحدة فقط ولا يمكنها الامتداد عبر مناطق متعددة. كذلك، كل شبكة فرعية (Subnet) مرتبطة بمنطقة توافر (Availability Zone) واحدة فقط. لتحقيق التوافر العالي، يُنشئ المهندسون شبكات فرعية متعددة في مناطق توافر مختلفة داخل نفس الـ VPC.

No to both. A VPC belongs to one Region only and cannot span multiple Regions. A subnet belongs to one Availability Zone only. For high availability, architects create multiple subnets across different AZs within the same VPC.

نطاقات CIDR المتداخلة

Overlapping CIDR Blocks
صعب

مهندس شبكات أنشأ VPC بـ CIDR 10.0.0.0/16، ثم حاول إنشاء ثلاث شبكات فرعية بالنطاقات التالية: 10.0.0.0/24 و10.0.0.128/25 و10.0.1.0/24. رفض AWS إنشاء الشبكة الثانية. لماذا؟

A network engineer created a VPC (10.0.0.0/16) and tried to create three subnets: 10.0.0.0/24, 10.0.0.128/25, and 10.0.1.0/24. AWS rejected the second subnet. Why?

ما سبب الرفض، وكيف يمكن إصلاحه؟

Why was the second subnet rejected, and how can it be fixed?

✔ الإجابة

الشبكة الثانية 10.0.0.128/25 تتداخل مع الأولى 10.0.0.0/24 — كلاهما يشملان عناوين 10.0.0.128 إلى 10.0.0.255. لا تسمح AWS بتداخل نطاقات CIDR بين الشبكات الفرعية داخل نفس الـ VPC. الحل: استخدام نطاق لا يتداخل مثل 10.0.2.0/25.

10.0.0.128/25 overlaps with 10.0.0.0/24 — both include addresses 10.0.0.128–10.0.0.255. AWS does not allow overlapping CIDR blocks within the same VPC. Fix: use a non-overlapping range like 10.0.2.0/25.

CIDR Overlapping VPC Design

واجهة الشبكة المرنة

Elastic Network Interface (ENI)
متوسط

شركة تشغّل تطبيقاً يتطلب شبكتين منفصلتين: واحدة للمستخدمين (10.0.1.0/24) وأخرى للإدارة (10.0.2.0/24). يريد الفريق خادماً واحداً EC2 يمكنه التواصل مع كلتا الشبكتين في آنٍ واحد.

A company needs one EC2 server to communicate with two separate subnets simultaneously: a user-facing subnet (10.0.1.0/24) and a management subnet (10.0.2.0/24).

كيف يمكن تحقيق ذلك في AWS؟

How can this be achieved in AWS?

✔ الإجابة

يمكن إرفاق Elastic Network Interface (ENI) إضافية بالـ instance. الـ instance لديه بالفعل واجهة شبكة أساسية (Primary ENI) في الشبكة الأولى. يُنشئ الفريق ENI ثانية في الشبكة الثانية ويرفقها بنفس الـ instance. يصبح الخادم قادراً على الاتصال بكلتا الشبكتين. عدد الـ ENIs التي يمكن إرفاقها يعتمد على نوع الـ instance.

Attach an additional Elastic Network Interface (ENI) to the EC2 instance. The instance already has a primary ENI in the first subnet. Create a second ENI in the management subnet and attach it to the same instance. The number of ENIs supported depends on the instance type.

NAT Instance مقابل NAT Gateway

NAT Instance vs NAT Gateway
متوسط

مدير تقنية معلومات في شركة ناشئة يناقش مع فريقه خياري NAT Instance وNAT Gateway لتمكين الخوادم الخاصة من الوصول إلى الإنترنت. يريد الحل الأقل تعقيداً إدارياً مع أداء أفضل.

A CTO is comparing NAT Instance vs NAT Gateway to allow private servers to access the internet. He wants the option with less admin overhead and better performance.

أي الخيارين توصي به AWS، وما الفرق الجوهري بينهما؟

Which option does AWS recommend, and what is the key difference?

✔ الإجابة

توصي AWS باستخدام NAT Gateway في معظم الحالات. فهو خدمة مُدارة بالكامل توفر توافراً أعلى وعرض نطاق ترددي أكبر وجهداً إدارياً أقل مقارنةً بـ NAT Instance الذي يتطلب إدارة يدوية وتحديثات وإعداد أمني. الـ NAT Gateway هو الخيار الأفضل للإنتاج.

AWS recommends NAT Gateway. It is fully managed, offers better availability, higher bandwidth, and requires less administrative effort than a NAT Instance, which needs manual management, patching, and security configuration.

NAT Gateway NAT Instance Managed Service

المسار المحلي في جدول التوجيه

Local Route in Route Table
سهل

أثناء مراجعة إعدادات الشبكة، حاول مهندس حذف المسار المحلي (local route) من جدول توجيه الـ VPC الخاص بـ CIDR 10.0.0.0/16. رفض AWS طلبه. لماذا؟ وما أهمية هذا المسار؟

During a network review, an engineer tried to delete the local route from a VPC route table (10.0.0.0/16). AWS refused. Why, and what is the purpose of this route?

لماذا لا يمكن حذف المسار المحلي، وما وظيفته؟

Why can't the local route be deleted, and what does it do?

✔ الإجابة

المسار المحلي هو مسار افتراضي يُضاف تلقائياً إلى كل جدول توجيه في الـ VPC، ولا يمكن حذفه أبداً. وظيفته هي تمكين الاتصال الداخلي بين جميع الموارد داخل نفس الـ VPC (10.0.0.0/16 → local). بدونه، لن تتمكن الموارد داخل الـ VPC من التواصل مع بعضها.

The local route is automatically added to every VPC route table and cannot be deleted. It enables internal communication between all resources within the same VPC (10.0.0.0/16 → local). Without it, resources inside the VPC cannot communicate with each other.
